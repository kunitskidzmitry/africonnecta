## 1. Продуктовый контекст `[SRC]`

Платформа связывает университеты, исследовательские институты, правительства, НКО и международные
организации с академическими экспертами из Африки и диаспоры. Отличие от обычных академических
директорий: верифицированная экспертиза + африканский контекст + AI-матчинг.

Ключевые сущности ценности:

- **African Context Score (ACS)** — 0–100, релевантность африканскому контексту. Пять компонентов.
- **AI Expert Matching** — ранжирование по 5 факторам с весами 40/25/15/10/10.

Роли: Academic Expert, Institution, Administrator.
Фаза 1: Руанда, 200 экспертов, 10 институций, запуск MVP.

## 2. Архитектурная стратегия `[FILL]`

### 2.1. Модульный монолит, не микросервисы

**Обоснование:** Фаза 1 — 200 экспертов и 10 институций. Это малые данные. Микросервисы,
очереди сообщений и отдельный поисковый кластер добавят месяцы к запуску и ноль пользы. Узкое
место проекта — качество данных и холодный старт двустороннего маркетплейса, а не нагрузка.

Границы модулей соблюдаются на уровне папок и публичных интерфейсов, чтобы при необходимости
любой модуль можно было вынести:

```
src/modules/
  identity/      — users, sessions, roles, institution membership
  profiles/      — expert profile, institution profile
  taxonomy/      — expertise, countries, languages (контролируемые словари)
  verification/  — ORCID, домен email, ручная модерация
  scoring/       — ACS + matching engine
  search/        — фасетный поиск и ранжирование
  opportunities/ — вакансии и заявки
  messaging/     — переписка
  notifications/ — in-app + email
  reviews/       — отзывы с модерацией          [Phase 1.5]
  billing/       — тарифы                        [Phase 1.5, см. §11]
  analytics/     — метрики для институций         [Phase 1.5]
  admin/         — Admin Console
```

**В Фазе 1 создаются не все модули** — объём сокращён под одного разработчика, см. §2.5.
Структура папок закладывается целиком, чтобы отложенные модули добавлялись без реорганизации.

**Правило зависимостей:** модуль импортирует только публичный `index.ts` другого модуля.
Прямой импорт внутренностей чужого модуля запрещён (линт-правило `import/no-restricted-paths`).

### 2.2. Стек `[DECIDED]` — Q1: соло-разработчик без бэкенд-опыта

Ответ заказчика: проект делает **один человек без опыта бэкенда**. Это главное ограничение
проекта, важнее любого технического предпочтения. Стек выбран так, чтобы минимизировать число
систем, которые надо самостоятельно эксплуатировать.

| Слой                | Выбор                                                                   | Обоснование                                                                                               |
| ------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Frontend + BFF      | Next.js (App Router) + TypeScript, `strict`                             | Один язык на весь стек, один деплой, SSR для SEO публичных профилей                                       |
| БД + Auth + Storage | **Supabase** (управляемый PostgreSQL с `pgvector`, `pg_trgm`, `citext`) | Три системы вместо трёх отдельных сервисов. Auth, presigned-хранилище и БД у одного провайдера            |
| Доступ к данным     | Drizzle поверх Supabase Postgres                                        | Типизированные запросы, миграции в git                                                                    |
| RLS                 | Включена на всех таблицах с персональными данными                       | **Второй рубеж** авторизации: даже при ошибке в коде БД откажет. Для неопытного разработчика это критично |
| Email               | Транзакционный провайдер с webhook на bounce                            | Приглашения — ядро цикла, доставляемость критична                                                         |
| Фоновые задачи      | Postgres-очередь (`pgboss`) или Supabase cron                           | Отдельный Redis на этом объёме не нужен                                                                   |
| Хостинг приложения  | Managed-платформа для Next.js                                           | Ноль администрирования серверов                                                                           |

**Регион Supabase: `eu-central-1` (Франкфурт).** Африканского региона у Supabase нет —
на момент проверки доступно 17 регионов, ни одного в Африке (запрос на Кейптаун
`af-south-1` был закрыт как feature request). Ближайшие варианты — Франкфурт или Париж.
Задержка Кигали→Франкфурт порядка 150–180 мс, поэтому публичные страницы (профили, лендинг)
обязаны отдаваться SSR + кеш на CDN, а не собираться клиентскими запросами к БД.

**Не использовать в Фазе 1:** Elasticsearch, Kafka, отдельный сервис матчинга, GraphQL,
микрофронтенды, Kubernetes. Каждое из этого — отложенное решение, а не запрет навсегда.

### 2.2.1. Компенсация неопытности `[FILL]`

Соло-разработчик без бэкенд-опыта допускает ошибки в предсказуемых местах. Механические
предохранители, которые ловят их без ревьюера:

1. **RLS на всех таблицах с персональными данными.** Ошибка в коде приложения не приводит к
   утечке, потому что БД отказывает независимо. Политики покрываются тестами из §12.
2. **Никакой конкатенации SQL.** Только параметризованные запросы через ORM. Линт-правило.
3. **Типы от БД до UI.** Схема → типы Drizzle → валидация ввода (Zod) на каждой границе.
   Ошибка формата данных ловится компилятором, а не в проде.
4. **CI обязателен с первого дня:** типы, линт, тесты матрицы авторизации §8.1. Красный CI
   блокирует мерж. Это заменяет второго разработчика.
5. **Бэкапы с проверенным восстановлением.** Бэкап, из которого ни разу не восстанавливались,
   бэкапом не является. Пробное восстановление — в M0, не в M7.
6. **Никаких секретов в клиентском коде.** Supabase `anon key` уходит в браузер и это нормально,
   `service_role key` — **только на сервере**. Утечка service-role-ключа = полный доступ к базе
   в обход RLS. Проверка в CI на наличие ключа в клиентском бандле.

### 2.3. Резидентность данных `[LEGAL]` `[DECIDED]` Q2

Закон Руанды № 058/2021 «relating to the protection of personal data and privacy» (в силе с
15.10.2021) требует хранить персональные данные **в Руанде**. Хранение за пределами страны
допускается при наличии разрешения надзорного органа (NCSA / Data Protection Office). Для
получения разрешения подаются: заявление на имя CEO NCSA, заполненная форма, хостинговый договор
и DPIA. Регистрация в качестве data controller обязательна. Закон имеет экстерриториальный охват:
применяется и к контролёрам вне Руанды, если обрабатываются данные субъектов в Руанде.

**Решение заказчика: зарубежный PaaS + разрешение NCSA + DPIA.** Это согласуется с §2.2
(соло-разработчику нечем администрировать собственный дата-центр), но переносит работу с кода
на бумаги.

**Разрешительный трек идёт параллельно разработке и стартует в M0, а не в M7.** Он длиннее, чем
кажется, и способен задержать запуск сильнее, чем любая техническая задача:

| Шаг | Артефакт                                                               | Когда                 |
| --- | ---------------------------------------------------------------------- | --------------------- |
| 1   | Регистрация в качестве data controller в Data Protection Office (NCSA) | M0                    |
| 2   | Заявление на имя CEO NCSA + заполненная форма на внешнее хранение      | M0–M1                 |
| 3   | Хостинговый договор с провайдером (Supabase + платформа приложения)    | M1                    |
| 4   | **DPIA** для хранения персональных данных за пределами Руанды          | M2–M3                 |
| 5   | Получение разрешения                                                   | до публичного запуска |

Для DPIA понадобится реестр обработки, поэтому **веди его с M0**: какие категории данных, зачем,
где хранятся, кому передаются, сроки хранения. Дописать его задним числом перед запуском —
типовая причина срыва сроков.

Инженерные следствия, которые закладываем сразу: единый список внешних получателей данных
(каждый новый сторонний сервис = изменение в разрешении), сроки хранения на уровне схемы БД,
экспорт и удаление данных по запросу субъекта.

Требование проверено по тексту закона и по форме заявки NCSA, но **обязательна проверка местным
юристом** — я не юрист, и содержание DPIA согласовывается с ним.

### 2.4. Регуляторный статус ранжирования `[LEGAL]`

Ранжирование людей под вакансии подпадает под Annex III п. 4(a) EU AI Act («recruitment or
selection of natural persons... to evaluate candidates») как высокорисковое. Обязанности для
Annex III применяются с 2 августа 2026.

Применимость к AfriConnecta неоднородна:

- **Фаза 1** (гостевые лекции, научное сотрудничество, менторство) — спорно, скорее «talent
  community matching», а не рекрутинг.
- **Фаза 4** («Academic Jobs») — однозначно рекрутинг.

Регламент применим при работе с субъектами в ЕС, а «диаспора» по определению включает резидентов
ЕС. Технические предпосылки, которые закладываем **сразу**, чтобы не переписывать позже:

1. Детерминированное объяснимое ранжирование (не LLM) — §6.
2. Логирование каждого прогона матчинга с сохранением вклада каждого фактора (`match_runs`,
   `match_results`). Срок хранения ≥ 6 месяцев.
3. Человек в контуре: платформа выдаёт ранжированный список, решение принимает институция.
   Автоматического отказа кандидату нет ни в одном сценарии.
4. Право эксперта увидеть свой ACS с разбивкой по компонентам и оспорить его.
5. Никакого вывода характеристик из фото, видео или голоса.

**Не юридическое заключение.** Требуется оценка юриста до выхода на институции из ЕС.

Тринадцать модулей из §2.1 в одиночку не строятся. Ниже — что действительно входит в Фазу 1.
Критерий отбора: **без чего 200 экспертов и 10 институций не смогут найти друг друга и
договориться.** Всё остальное — Phase 1.5.

| Модуль                               | Фаза 1         | Обоснование                                                                                |
| ------------------------------------ | -------------- | ------------------------------------------------------------------------------------------ |
| identity, profiles, taxonomy         | ✅             | Без этого нет продукта                                                                     |
| search                               | ✅             | Основной сценарий                                                                          |
| opportunities + applications         | ✅             | `[SRC §7]`, второй сценарий                                                                |
| messaging                            | ✅ урезанный   | Только текст. Без вложений, реакций, групповых чатов                                       |
| notifications                        | ✅ урезанный   | Только email + счётчик в шапке. Без настроек и дайджестов                                  |
| verification                         | ✅ урезанный   | Только домен email + ручная проверка админом. ORCID → Phase 1.5                            |
| scoring (ACS + matching)             | ✅             | Ключевое отличие продукта, вынести нельзя                                                  |
| admin                                | ✅ минимальный | Очередь верификации + разблокировка. Всё прочее — прямо в БД                               |
| **billing**                          | ❌             | Решение Q3, см. ниже                                                                       |
| **reviews**                          | ❌             | Требует модерации, то есть постоянного человеческого труда. На 10 институциях бессмысленно |
| **analytics для институций**         | ❌             | Админу нужна одна метрика: доля пустых выдач §10. Остальное — SQL-запросы руками           |
| **Team Members / мультитенантность** | ❌             | См. ниже — это самое ценное сокращение                                                     |

**Мультитенантность откладывается: один пользователь = одна институция.** В макете есть «Team
Members», но в Фазе 1 институций десять, и у каждой будет один контактный человек. Отказ от
мультипользовательских аккаунтов убирает целый класс уязвимостей — именно на границах тенантов
живут IDOR-ошибки, а поймать их без опыта и без ревьюера тяжелее всего.

Таблица `institution_members` **всё равно создаётся** и содержит ровно одну строку с ролью
`owner` на институцию. Код с первого дня ходит через неё, а не через `institutions.owner_user_id`.
Тогда включение полноценных команд в Phase 1.5 — это добавление UI приглашений, а не
переписывание модели доступа.

**Реалистичность сроков.** Восемь вех §11 в одиночку и с нуля — это не недели. Если сроки
поджимают, режется не качество кода и не §9 (безопасность), а объём: Opportunity Board можно
запустить после поиска, ACS можно временно считать по трём компонентам из пяти. Что нельзя
урезать никогда: авторизацию §8, правила загрузки файлов §9 и бэкапы.

## 3. Заполнение пропущенных разделов Functional Spec `[FILL]`

Источник содержит §4–8 и §14–15. Ниже — реконструкция §1–3 и §9–13. Нумерация §9–13 выведена из
списка экранов в `• Search & Filters.pdf` (Messaging Center, Analytics Dashboard, Admin Console),
который заполняет ровно этот промежуток. **Это обоснованная догадка, а не восстановленный
оригинал.**

### §1. Purpose & Scope

MVP обслуживает один географический рынок (Руанда) и три роли. Успех Фазы 1 измеряется не
нагрузкой, а плотностью данных: 200 заполненных верифицированных профилей и 10 активных институций.

### §2. Definitions

- **Expert** — физлицо с подтверждённой академической аффилиацией или учёной степенью.
- **Institution** — организация-аккаунт с несколькими участниками (Team Members).
- **Engagement** — состоявшееся взаимодействие (принятая заявка или приглашение). Основание для
  отзыва и метрики «Collaborations Facilitated».
- **Verified** — статус, подтверждённый внешним источником или админом, с фиксацией метода.

### §3. Personas & Non-Functional Requirements

Целевая среда — мобильный интернет в Восточной Африке. Отсюда бюджеты:

| Показатель                    | Бюджет                                                                   |
| ----------------------------- | ------------------------------------------------------------------------ |
| JS в первичной загрузке       | ≤ 200 KB gzip                                                            |
| LCP на Slow 4G                | ≤ 2.5 s                                                                  |
| p95 серверного времени поиска | ≤ 300 ms при 100k профилей                                               |
| Работа без JS                 | Поиск и просмотр профиля должны работать (SSR + прогрессивное улучшение) |
| Языки интерфейса              | EN обязателен, FR — см. `[BLOCKED]` Q6                                   |
| Доступность                   | WCAG 2.1 AA                                                              |

Изображения — WebP/AVIF с ресайзом на сервере. Фото профилей не отдаются в оригинальном размере.

### §9. Messaging `[FILL]`

Переписка на уровне разговора (`conversations` + `conversation_participants` + `messages`).

**Антиабьюз-правила, без них модуль превращается в спам-канал:**

- Институция может начать разговор с экспертом только при: верифицированном аккаунте института
  **и** остатке квоты по тарифу.
- Эксперт может ответить всегда; исходящий первый контакт от эксперта — только по опубликованной
  вакансии.
- Контакты (email, телефон) не подставляются в тело сообщения автоматически и не отдаются API.
- Рейт-лимит: N первых контактов в сутки на институцию, M на пользователя.
- Кнопка «Report» на каждом разговоре, флаг уходит в Admin Console.

### §10. Notifications `[FILL]`

Типы: `invitation_received`, `application_received`, `application_status_changed`,
`message_received`, `verification_result`, `opportunity_deadline`, `acs_recomputed`.

Доставка: in-app всегда, email — по настройкам пользователя, дайджестом раз в сутки по умолчанию
для `message_received` (мгновенно — только для приглашений и статусов заявок). Отправка идёт через
очередь с идемпотентным ключом, чтобы ретрай не задваивал письма. Обработка bounce и unsubscribe
обязательна.

### §11. Verification & Trust `[FILL]`

Три независимых уровня, отображаются раздельно, не схлопываются в один бейдж:

| Уровень     | Метод                                                 | Что подтверждает                       |
| ----------- | ----------------------------------------------------- | -------------------------------------- |
| Identity    | Email (Фаза 1). ORCID — Phase 1.5                     | Человек существует и владеет аккаунтом |
| Affiliation | Email на домене института или ручная проверка админом | Связь с институцией                    |
| Scholarship | Публикации по ORCID / DOI — Phase 1.5                 | Академический след                     |

**ORCID: важное ограничение, проверенное по первоисточнику.** ORCID публикует OIDC discovery по
адресу `https://orcid.org/.well-known/openid-configuration` (issuer `https://orcid.org`), и
Supabase Auth умеет подключать произвольные OIDC-провайдеры. Но в discovery-документе ORCID:

- `scopes_supported` содержит **только** `openid`;
- `claims_supported` — это `family_name`, `given_name`, `name`, `auth_time`, `iss`, `sub`.
  **Email там отсутствует.**
- `token_endpoint_auth_methods_supported` — только `client_secret_post`.

Следствия: запрашивать скоупы `profile` и `email` бесполезно, письмо от ORCID не придёт, и
провайдер в Supabase придётся создавать с `email_optional: true`. Поэтому **ORCID не может быть
основным способом регистрации** — аккаунт создаётся по email, а ORCID привязывается к нему
позже как подтверждение научной личности. Это ровно та роль, которая нужна для §5.2, так что
ограничение не мешает замыслу, но ломает наивную схему «вход через ORCID».

Институции верифицируются отдельно: сверка домена сайта и, где возможно, идентификатора в ROR.

**Заявляемые пользователем поля никогда не отображаются как «verified».** В UI различаются
«claimed» и «verified» — иначе весь ACS обесценивается.

### §12. Analytics & Reporting `[FILL]`

Для институции: просмотры вакансий, отклики, конверсия приглашение→engagement, использование квот.
Для админа: рост профилей, доля верифицированных, покрытие по странам и областям экспертизы, доля
поисков с пустой выдачей (**ключевая метрика холодного старта**), распределение ACS.

Аналитика считается по событиям в собственной БД. Внешние трекеры на страницах с персональными
данными не ставим — см. §2.3.

### §13. Admin Console `[FILL]`

Очередь верификации, модерация отзывов и жалоб, управление таксономией (экспертиза, страны,
языки), ручной пересчёт ACS с указанием причины, просмотр аудит-лога, управление тарифами.

**Все действия админа пишутся в `audit_log` с actor, действием, объектом и причиной.** Админ
не может редактировать ACS напрямую — только оспорить входные данные и запустить пересчёт.

## 4. Модель данных `[FILL]`

### 4.1. Identity & tenancy

`institution_members` — это таблица мультитенантности. **Каждый запрос к данным института

### 4.2. Профили

```sql

        current_institution_id,    -- FK, nullable
```

**Про `current_institution`.** В источнике `[SRC §4]` это поле регистрации эксперта, то есть
свободный текст. Но в Фазе 1 на платформе будет 10 институций, а экспертов — 200: у большинства

## 5. African Context Score `[FILL]` веса + `[DECIDED]` Q4 структура

Источник даёт пять компонентов, но **не даёт весов**. Ниже — предложение, требующее подтверждения.

### 5.1. Предлагаемые веса

| Компонент `[SRC]`               | Вес `[FILL]` | Что измеряет                                                |
| ------------------------------- | ------------ | ----------------------------------------------------------- |
| Academic Engagement             | 25           | Преподавание/исследования в африканских институциях, годы   |
| Geographical Expertise          | 25           | Число и глубина связей со странами Африки                   |
| Policy & Development Experience | 20           | Работа с правительствами, НКО, международными организациями |
| Diaspora Contribution           | 15           | Вклад в африканскую науку из-за рубежа                      |
| Language & Cultural Competency  | 15           | Владение африканскими языками, культурный контекст          |
| **Итого**                       | **100**      |                                                             |

### 5.2. Множитель достоверности — обязателен

Каждый компонент считается как `raw_score × confidence`, где:

| Источник данных                                                            | confidence |
| -------------------------------------------------------------------------- | ---------- |
| Заявлено пользователем, без подтверждения                                  | 0.50       |
| Подтверждено загруженным документом                                        | 0.80       |
| Подтверждено внешним источником (ORCID / OpenAlex / ROR / домен института) | 1.00       |

**Без этого механизма ACS деградирует за месяцы.** Все поля («страны работы», «опыт в политике»,
«вклад диаспоры») заполняет сам эксперт, а балл влияет на позицию в выдаче — то есть стимул к
накрутке встроен в продукт. Множитель делает верификацию выгодной вместо того, чтобы делать
преувеличение выгодным.

Правила: балл считается **только на сервере**, эксперт не может его редактировать, пересчёт при
изменении входных данных и по расписанию, каждая версия сохраняется, в UI показывается разбивка
по компонентам с указанием, что именно снижает балл.

### 5.3. Компонент «Diaspora Contribution» — симметричный `[DECIDED]` Q4

**Исходный дефект.** Профессор Университета Руанды, живущий в Кигали, получал бы по этому
компоненту **ноль** и терял 15 баллов относительно руандийца в Торонто с сопоставимым профилем.
Платформа, чья миссия — «сделать африканскую экспертизу видимой и влиятельной», начала бы
систематически поднимать диаспору над локальными академиками.

**Решение заказчика: симметричный вариант.** Компонент считается как

```
contribution = max(local_presence, diaspora_contribution)
```

где `local_presence` — вклад через работу внутри Африки (аффилиация с африканской институцией,
преподавание, руководство аспирантами, местные публикации), а `diaspora_contribution` — вклад
извне (соавторство с африканскими институциями, дистанционное менторство, приглашённые курсы,
совместные гранты).

Обе формы засчитываются, ни одна не наказывается за место жительства. Название компонента в UI
меняется на нейтральное; внутренняя разбивка `local` / `diaspora` сохраняется в
`african_context_scores.components` для аналитики, но на итог влияет только максимум.

**Обязательный тест справедливости (§12).** Два синтетических профиля, идентичных во всём, кроме
страны проживания (Кигали против Торонто), обязаны получать сопоставимый ACS. Расхождение больше
порога — падение сборки. Без этого теста регрессия вернётся при первой же правке весов.

## 6. Матчинг `[SRC]` веса + `[FILL]` механика

### 6.1. Веса из источника — не менять

```
match_score = 0.40 · expertise
            + 0.25 · african_context_score
            + 0.15 · research_relevance
            + 0.10 · language_match
            + 0.10 · availability
```

Все факторы нормализуются в `[0, 1]`, итог — в проценты (пример источника: 92%).

### 6.2. Двухстадийное ранжирование — обязательно

**Проблема прямого применения формулы:** ACS весит 25%, поэтому эксперт с идеальным попаданием по
теме и ACS 40 проигрывает нерелевантному с ACS 95. Это ломает главное обещание продукта.

```
Стадия 1 — отбор (hard filters):
    страна/регион, язык (если обязателен), формат работы, академический уровень
    → множество кандидатов

Стадия 2 — порог релевантности:
    отбросить всех с expertise < EXPERTISE_FLOOR (стартовое значение 0.35)
    → ACS физически не может вытащить нерелевантного эксперта наверх

Стадия 3 — ранжирование:
    применить формулу §6.1 к top-N (N ≈ 500), сохранить вклад каждого фактора
```

Побочный эффект: стадии 1–2 отсекают почти всё до дорогого этапа, поэтому бюджет p95 ≤ 300 ms
достигается на обычном Postgres без поискового кластера.

### 6.3. Определения факторов

**expertise** = `0.6 · tag_overlap + 0.4 · cosine(query_embedding, profile_embedding)`,
где `tag_overlap` — взвешенное пересечение по иерархии областей экспертизы (совпадение
родительской категории засчитывается частично).

**african_context_score** = `ACS / 100` из §5.

**research_relevance** = близость тем публикаций к запросу с затуханием по давности.
**Важно:** при отсутствии публикаций подставляется нейтральное `0.5`, а не `0`. Ноль означал бы
систематический штраф раннекарьерным исследователям и всем, кто ещё не подключил ORCID — а в Фазе
1 это будет большинство из 200 профилей.

**language_match** — 1.0 при C1+, 0.7 при B2, 0 ниже. Если язык не задан в запросе — 1.0.

**availability** — 1.0 при точном совпадении формата, 0.6 при совместимом (hybrid ↔ online/onsite),
0 при несовместимом.

### 6.4. Почему не LLM

LLM в цикле ранжирования даёт недетерминированность (один запрос — разный порядок), задержку
секундного порядка, стоимость на каждый поиск и невозможность объяснить эксперту его позицию.
Последнее прямо конфликтует с §2.4. LLM и эмбеддинги применяются **только** для вычисления
семантической близости (одного признака из пяти) и для офлайн-задач: нормализация тегов,
предложение областей экспертизы при заполнении профиля.

**`[ASSUMED]`:** мультиязычные эмбеддинги плохо покрывают киньяруанда. Поэтому канонический текст
профиля для эмбеддинга хранится на английском, а язык остаётся **фасетом фильтрации**, а не
предметом кросс-язычного семантического поиска. Проверить на реальных данных до релиза.

## 7. API `[SRC]` основа + `[FILL]` полный контур

Источник даёт 7 эндпоинтов без пагинации, фильтров, модели ошибок и версионирования. Полный контур:

до чтения тела. Оформить как ADR-001.

| **Загрузка файлов (CV, фото)**                             | Presigned upload напрямую в хранилище; whitelist MIME с проверкой сигнатуры файла, а не расширения; лимит размера; антивирус-скан до публикации; отдача с отдельного домена; `Content-Disposition: attachment`; удаление EXIF из фото |
| **Накрутка ACS**                                           | Множитель достоверности §5.2; расчёт только на сервере; версионирование                                                                                                                                                               |
| **Спам от институций**                                     | Квоты первого контакта; верификация института до права писать; Report                                                                                                                                                                 |
| **Захват «claimable» профилей** (при засеве базы админами) | Активация только через email на домене института или ручную проверку; ссылки одноразовые с TTL                                                                                                                                        |
| **Диффамация в отзывах**                                   | Отзыв только при наличии `engagement`; премодерация; право эксперта на ответ; фиксация авторства                                                                                                                                      |
| **Утечка через уведомления**                               | В email не кладём тело сообщения и персональные данные — только ссылку                                                                                                                                                                |
| **Перебор паролей / регистрации**                          | Rate limit, экспоненциальная задержка, CAPTCHA при аномалиях, argon2id для хэшей                                                                                                                                                      |

Базовая гигиена, не обсуждается: параметризованные запросы, CSP без `unsafe-inline`, HttpOnly +
SameSite cookies, CSRF-токены на мутациях, HSTS, секреты не в git, зависимости под аудитом.

## 10. Холодный старт `[FILL]`

**Это главный риск провала, и он не технический.** Двусторонний маркетплейс с пустой выдачей
умирает раньше, чем упрётся в производительность. 200 экспертов на всю Руанду означает, что
специализированный запрос вернёт ноль результатов.

Обязательно в MVP, а не «потом»:

1. **Метрика «доля поисков с пустой выдачей»** на дашборде админа — главный индикатор здоровья.
2. **Никогда не показывать пустой экран.** Нет точных совпадений → показать ближайшие по
   иерархии экспертизы с честной пометкой «расширенный поиск».
3. **Подписка на запрос:** «уведомить, когда появится эксперт по этой теме».
4. **Засев базы** через админ-импорт профилей с публичных источников — но каждый такой профиль
   помечен `unclaimed`, не показывает контактов и активируется только владельцем (см. §9).

## 12. Тестирование `[FILL]`

- **Матрица авторизации** — по тесту на каждую пару (роль, эндпоинт). Не опционально.
- **Golden-тесты скоринга:** фиксированный набор профилей → ожидаемые ACS и порядок выдачи.
  Ловят регрессии при правке весов.
- **Тесты справедливости:** синтетические пары профилей, отличающиеся только страной проживания
  или полом → проверка отсутствия систематического сдвига. Прямо поддерживает §2.4.
- **Сид реалистичных данных:** ≥ 10k профилей с правдоподобным распределением для проверки
  производительности. Не 20 записей.
- **E2E** на три критических пути: регистрация→профиль→публикация; поиск→контакт→engagement;
  вакансия→заявка→решение.

## 13. Definition of Done

Фича готова, когда: политика доступа объявлена и покрыта тестом; списочные ответы не содержат
персональных данных сверх необходимого; ошибки в формате RFC 9457; миграция обратима; бюджеты
производительности §3 соблюдены; строки локализованы; действия админа пишутся в audit_log;
изменения алгоритма скоринга сопровождаются ADR и обновлением golden-тестов.
