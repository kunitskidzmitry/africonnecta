# Восстановление из бэкапа

Критерий готовности M0: бэкап, из которого ни разу не восстанавливались, бэкапом не
является. Эта страница описывает, как снять дамп и как проверить, что он поднимается.

## Что хранится

| Что              | Где                             | В git |
| ---------------- | ------------------------------- | ----- |
| Схема            | `supabase/migrations/`          | да    |
| Справочники      | миграция `*_reference_data.sql` | да    |
| Тестовые профили | `supabase/seed.sql`             | да    |
| Дамп живой базы  | `backups/` (локально)           | нет   |

Исходные PDF в `docs/source/` в git не входят — их надо копировать отдельно.

## Локальный учебный прогон

Нужны запущенный Docker и `psql`. `pg_dump` / `pg_restore` берутся из контейнера
`supabase_db_*`: хостовый клиент на этой машине старше сервера (14 vs 17) и
отказался снимать дамп.

```bash
npm run db:start
npm run db:reset     # известное состояние: миграции + сид
npm run db:drill     # дамп → truncate → restore → сверка
```

`db:drill` снимает data-only дамп **пользовательских** таблиц (не справочников),
уничтожает их строки и поднимает обратно. Справочники остаются из миграций.
Маркер восстановления — эксперт `Yves Habimana`.

Снять дамп без уничтожения данных:

```bash
npm run db:dump      # backups/public.dump
```

## Облачный проект (после появления прод-инстанса)

1. Включить ежедневные бэкапы в панели Supabase (Point-in-time recovery на платном плане,
   ежедневные снапшоты — на бесплатном).
2. Раз в квартал: поднять копию из снапшота в отдельный проект и прогнать
   `npm run test:integration` против копии.
3. Зафиксировать дату прогона в этом файле.
