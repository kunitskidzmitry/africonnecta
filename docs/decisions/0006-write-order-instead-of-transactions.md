# ADR-0006. Целостность многотабличной записи держится порядком запросов, а не транзакцией

- **Статус:** принято
- **Дата:** 2026-09-06
- **Контекст:** §6.3 `docs/implementation-prompt.md` (профиль обязан находиться поиском),
  ADR-0003 (SQL-миграции вместо ORM)

## Контекст

Сохранение профиля эксперта затрагивает три таблицы: `experts`, `expert_expertise`,
`expert_languages`. PostgREST выполняет каждый запрос в собственной транзакции и не даёт
объединить несколько запросов в одну. Клиент Supabase поверх него — тоже.

Значит, сохранение профиля — это последовательность независимых записей, и оборваться она
может на любой из них: упал процесс Next, разорвалась сеть, посетитель закрыл вкладку.

Опасное состояние одно: профиль опубликован (`published_at is not null`), но не имеет ни
одной области экспертизы или ни одного языка. По §6.3 поиск ранжирует именно по этим
связям, поэтому такой профиль не находится вообще. Человек видит «опубликовано» и не
получает ни одного обращения, причём молча и неограниченно долго.

## Решение

Инвариант **«опубликован ⇒ есть хотя бы одна область и хотя бы один язык»** держится
порядком запросов. Порядок задаёт `planProfileWrite` в `src/lib/profile/write-plan.ts` —
чистая функция, возвращающая список шагов; server action только исполняет их подряд.

Правил два.

1. **Публикация снимается первым запросом и ставится последним.** Пока связи в движении,
   профиль либо черновик, либо опубликован с прежним полным набором.
2. **Внутри связей вставки идут перед удалениями.** Промежуточное состояние — объединение
   старого и нового набора, оно непусто по построению.

Второе правило появилось не сразу. Первая версия удаляла до вставки, и при полной замене
набора (было «экономика», стало «агрономия») между удалением и вставкой опубликованный
профиль оставался без областей — то самое состояние, которое инвариант запрещает.

## Обоснование

Транзакцию можно было бы получить, завернув всю запись в функцию `security definer` и
вызвав её через RPC. От этого отказались: тело такой функции повторило бы всю проверку
прав, которую сейчас выполняет RLS, и обошло бы её же. Каждая ошибка в SQL-теле
становилась бы дырой в авторизации, а по AGENTS.md §3 «deny by default» и по матрице §8.1
права проверяются политиками, а не процедурным кодом.

Порядок запросов даёт то же свойство дешевле: сбой посередине оставляет профиль в
предыдущем целом состоянии, а не в противоречивом. Лишняя область экспертизы, которую
может оставить обрыв, безобиднее пустого опубликованного профиля на несколько порядков.

Чистая функция вместо порядка вызовов внутри действия — потому что порядок стал единственной
защитой инварианта, а порядок, размазанный по потоку управления, нельзя предъявить тесту.
Планом можно: `tests/profile-write-plan.test.ts` прогоняет каждый префикс плана на модели
трёх таблиц, `tests/integration/profile.test.ts` — те же шаги настоящими запросами к
настоящей базе, читая состояние после каждого. Оба теста падают, если поменять порядок
местами; проверено переворотом.

## Последствия

- Любая новая многотабличная запись обязана либо расширить `planProfileWrite`, либо
  завести собственный план с таким же тестом на префиксы. Последовательность
  `await` подряд в server action без такого теста — регрессия, а не стиль.
- Инвариант в базе не закреплён. Ограничением его не выразить: `check` не видит другие
  таблицы, а триггер на `experts` не поймает удаление последней строки из
  `expert_expertise`. Ограничивающий триггер на все три таблицы возможен, но заблокировал
  бы законный порядок «снять публикацию → почистить связи» и потребовал бы отложенной
  проверки на уровне транзакции, которой у PostgREST нет.
- Поэтому единственный настоящий предохранитель — тесты. Удаление любого из двух ломает
  инвариант молча.
