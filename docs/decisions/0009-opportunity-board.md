# ADR-0009. Opportunity Board: ref_value, engagement-триггеры, матчинг в M5

- **Статус:** принято
- **Дата:** 2026-09-08
- **Контекст:** §4.6, §7, §11 M3 `docs/implementation-prompt.md`

## Контекст

M3 требует полный цикл вакансия → заявка/приглашение → engagement. Черновик схемы
§4.6 и API §7 задают таблицы и эндпоинты, но не enum-значения, не политики доступа
для заявок и не момент создания `engagements`.

## Решения

**1. `opportunity_requirements.ref_value text` вместо `ref_id`.**

У `kind = academic_level` нет числового идентификатора в справочнике — это enum
`academic_level`. Общий `ref_id integer` ломал бы эту ветку. Храним строковый ключ:
id экспертизы/языка/страны или литерал уровня. Таблица в M3 есть; UI требований
может появиться позже.

**2. `engagements` пишет только триггер.**

Клиентский insert закрыт (deny by default). При `applications.status = accepted` или
`invitations.status = accepted` security definer-триггер создаёт engagement. Это
закрывает накрутку «Collaborations Facilitated» и даёт основание для отзывов (§4.7)
без отдельного RPC на каждый путь.

**3. Матчинг (`GET /matches`, `match_runs`) не входит в M3.**

Критерий M3 — доска, заявки, приглашения и цикл до engagement. Ранжирование и журнал
прогонов — критерий M5 (§11). Заглушка в коде не нужна: эндпоинта просто нет.

**4. Доступ к данным — RLS + триггеры-гарды, без `/api/v1` в этой поставке.**

Как у профиля и поиска: клиент ходит в PostgREST под своей сессией, политики
повторяют матрицу §8.1. Server Actions валидируют формы; авторизация остаётся в БД.
