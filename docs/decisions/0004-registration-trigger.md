# ADR-0004. Профиль при регистрации создаёт триггер базы, а не приложение

- **Статус:** принято
- **Дата:** 2026-09-06
- **Контекст:** WP3 вехи M0, «Feature 1: Registration» (§4 Functional Spec)

## Контекст

Учётные данные хранит Supabase Auth в схеме `auth`, профили приложения — в `public`:
`users`, `experts`, `institutions`, `institution_members`. Регистрация обязана создать
записи в обеих областях, и обе либо появляются, либо не появляется ни одна.

Приложение не может выполнить это одной транзакцией: `signUp` — это HTTP-вызов к сервису
GoTrue, а вставка профиля — запрос к Postgres. Между ними нет общего контекста транзакции.

## Решение

Профиль создаёт триггер `on_auth_user_created` на `auth.users`, читая данные регистрации
из `raw_user_meta_data`. Второй триггер, `on_auth_user_email_confirmed`, переводит
`users.status` из `pending` в `active` при появлении `email_confirmed_at`.

## Обоснование

Триггер `AFTER INSERT` выполняется внутри транзакции, которой GoTrue создаёт учётную
запись. Исключение в триггере откатывает создание пользователя целиком. Осиротевших
учётных записей не бывает по построению — это проверяется тестом: после отклонённой
регистрации в `auth.users` не остаётся строки.

Рассмотренная альтернатива — вставка профиля вторым запросом со служебным ключом
и компенсирующее удаление пользователя при неудаче. Отвергнута по трём причинам:

1. Компенсация сама может не выполниться (сеть, перезапуск процесса), и тогда остаётся
   ровно то состояние, которого мы избегаем: войти можно, приложения для пользователя нет,
   повторно зарегистрироваться на тот же адрес нельзя.
2. Потребовался бы служебный ключ, обходящий RLS. Ключ, которого в проекте нет,
   невозможно случайно опубликовать в клиентском бандле.
3. Порядок операций пришлось бы повторять в каждом новом сценарии регистрации.

Второй триггер (активация) выбран вместо обработки в маршруте подтверждения потому,
что письмо открывают на другом устройстве чаще, чем на том же. Наш обработчик в этом
случае может не выполниться вовсе, а база факт подтверждения видит всегда.

## Граница доверия

Публикуемый ключ Supabase лежит в клиентском бандле по замыслу. Значит `signUp` можно
вызвать напрямую, минуя наши формы и валидацию на Zod. Поэтому триггер проверяет данные
повторно и сам решает, какая роль допустима:

- роль берётся из белого списка `expert` и `institution_member`; `admin` через регистрацию
  не выдаётся ни при каких метаданных;
- страна обязана существовать в справочнике `countries`;
- обязательные поля профиля проверяются на непустоту.

Валидация в форме — это удобство для пользователя. Валидация в триггере — граница доверия.

Функции объявлены `security definer` с `set search_path = ''` и полными именами таблиц:
без этого вызывающий может подменить схему и увести запись в свои таблицы.

## Последствия

- Данные регистрации проходят через `raw_user_meta_data`. Это не хранилище профиля,
  а транспорт: после создания записи источником правды становятся таблицы `public`.
- Ошибка триггера приходит клиенту как общий сбой сервера без подробностей. Для наших форм
  это не проблема — они валидируют данные заранее; в таком виде ошибку получают только
  запросы в обход интерфейса.
- Учётная запись без роли в метаданных профиль не получает и остаётся без прав. Этим
  пользуются `supabase/seed.sql` и создание администратора вручную.
