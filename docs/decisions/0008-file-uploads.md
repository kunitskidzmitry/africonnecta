# ADR-0008. Файлы идут через наш сервер, а не напрямую в хранилище

- **Статус:** принято
- **Дата:** 2026-09-06
- **Контекст:** §7 `docs/implementation-prompt.md` (загрузка файлов: whitelist MIME
  с проверкой сигнатуры, лимит размера, антивирус, удаление EXIF, отдача с отдельного
  домена), §9 (`scan_status = clean` как условие публикации), критерий M1 «файлы
  проверяются по сигнатуре»

## Контекст

Профилю эксперта нужны два файла: фотография и CV. Supabase Storage предлагает для этого
готовый путь — клиентский SDK кладёт файл в бакет сам, а RLS-политика на `storage.objects`
разрешает роли `authenticated` писать в папку со своим `user_id`. Это стандартный способ,
описанный в документации, и он не требует ни служебного ключа, ни обработчика на нашей
стороне.

Он несовместим с §7.

Три требования из §7 — проверка MIME по сигнатуре содержимого, лимит размера и удаление
EXIF — выполняются только над байтами файла. Байты есть у двух сторон: у загружающего
и у того, кому он их отправил. Если он отправляет их прямо в хранилище, у нас их нет
никогда, и проверять нечем.

Хуже того, проверку нельзя добавить рядом. Пока политика разрешает роли `authenticated`
писать в бакет, ровно те же права есть у браузера: можно не звать наш код и положить
в свою папку что угодно, объявив это `image/jpeg`. Проверка превращается в вежливую
просьбу, а критерий M1 — в проверку, которую обходят одним запросом из консоли.

## Решение

**1. Запись файлов — только через наш обработчик, служебным ключом.**

Клиентские роли не пишут ни в бакет `expert-files`, ни в `public.files`. Политик записи
для них нет ни одной: при включённом RLS отсутствие политики означает запрет, и это нужный
ответ (миграция `20260906230000_expert_files.sql`).

Загрузка идёт в `POST /api/files/upload`: он проверяет право вызывающего, читает байты,
опознаёт формат по сигнатуре, снимает метаданные и только после этого пишет в хранилище
служебным ключом. Служебный клиент живёт в одном файле (`src/lib/supabase/service.ts`)
и используется только для записи файлов; права на чтение по-прежнему решают политики.

Отличить наш сервер от браузера можно только тем, чего у браузера нет. Поэтому служебный
ключ здесь не удобство, а единственный доступный признак.

**2. Обработчик маршрута, а не server action.**

У server action тело ограничено одним мегабайтом, и поднимается предел только глобально
(`serverActions.bodySizeLimit`), то есть заодно для входа и сохранения профиля — форм,
которым большое тело не нужно никогда. Предел на файлы держится там, где он про файлы.

Плата: `/api` исключён из `proxy.ts` (`config.matcher`), поэтому проверку источника
server action сделал бы сам, а обработчик делает руками — `sameOrigin` в
`src/app/api/files/upload/route.ts`.

Выгода помимо лимита: обычная форма `method="post"` с `enctype="multipart/form-data"`
работает без JavaScript, ответ `303` возвращает браузер на страницу профиля. Результат
приезжает в строке запроса, поэтому оба значения проверяются по списку
(`src/lib/files/feedback.ts`): в разметку попадает ключ перевода, а не текст из адреса.

**3. Отдача — редиректом на подписанную ссылку, а не байтами через нас.**

`GET /api/files/[id]` читает строку файла клиентом вызывающего, просит у хранилища
подписанную ссылку и перенаправляет на неё. Так выполняется требование §7 «отдача
с отдельного домена»: содержимое приходит с домена Supabase, и файл, оказавшийся не тем,
чем притворяется, исполняется в чужом источнике, где ни наших куки, ни нашего DOM нет.

Право проверяет не этот код, а политика: подписать ссылку хранилище согласится только
если `expert_files_select` пропустит объект. Отсутствие права и отсутствие файла отвечают
одинаковым `404` — иначе перебором идентификаторов выясняется, у кого какой файл есть.

**4. Свой съёмник метаданных вместо перекодирования.**

`stripMetadata` (`src/lib/files/metadata.ts`) вырезает сегменты JPEG и чанки PNG,
не перекодируя изображение.

Перекодирование через `sharp` надёжнее: оно уничтожает всё, включая то, о чём мы
не подумали. Отказались из-за нативного бинарника в сборке — он привязывает образ
к платформе и версии libvips и на дешёвом хостинге (§2.2) ставится хуже всего остального
вместе. Разбор двух форматов, структура сегментов которых описана в стандарте, проверяется
точнее, чем «доверимся кодировщику»: тест утверждает, что байты APP1 исчезли, а пиксельные
данные остались теми же байтами (`tests/file-metadata.test.ts`, плюс проверка на реальных
фотографиях через `sips`).

Побочный эффект важнее основного: обрезается всё, что дописано после конца изображения.
Это самый простой способ спрятать в «фотографии» полезную нагрузку, и его не ловят
ни проверка сигнатуры (начало файла правильное), ни просмотр глазами.

**5. Антивирус отложен. `scan_status` остаётся `pending`.**

Сканера в Фазе 1 нет. Условие `scan_status <> 'infected'` в политиках чтения уже стоит
и пока не отсекает ничего.

Отложено потому, что ClamAV — это отдельный постоянно работающий процесс с базой
сигнатур в память, то есть либо второй контейнер, либо внешний сервис с оплатой
за проверку. Ни то ни другое не влезает в §2.2 на Фазе 1, а §9 требует `clean`
для публикации — то есть без сканера публикация встала бы вовсе.

Три вещи, которые эту отсрочку ограничивают:

- CV отдаётся с `Content-Disposition: attachment` и с чужого домена: браузер его
  не исполняет, а сохраняет.
- Фотография разобрана по сегментам, и дописанное за концом изображения отброшено.
- Условие в политиках уже врезано, так что появление сканера — это простановка статуса,
  а не правка политик во всех таблицах сразу.

**Это блокер запуска M7, а не закрытый вопрос.** Пока сканера нет, платформа хранит
и отдаёт файлы, которые никто не проверял на содержимое; для CV это прямая раздача
чужих PDF institution-ам.

## Последствия

- Служебный ключ появился в проекте. README и `.env.example` обновлены: до этой миграции
  оба утверждали, что ключа нет вовсе, и утверждение было частью модели безопасности.
  Теперь границей служит не отсутствие ключа, а единственное место его использования,
  и проверять это придётся глазами на ревью — механически CI ловит только утечку
  в клиентский бандл.
- Загрузка стоит нам трафика и памяти: файл проходит через наш процесс целиком.
  При лимитах 2 и 5 МБ и ожидаемом потоке (§2.2 — единицы загрузок в день) это ничто,
  но при росте первым упрётся именно этот путь, и тогда придётся возвращаться
  к подписанной ссылке на запись — с проверкой сигнатуры уже после загрузки и статусом
  файла до неё.
- Каждый новый принимаемый формат — это новая ветка в `detectFormat`, новый разбор
  в `stripMetadata` и новый тест. Расширять список по одному формату за раз.
- Прежние файлы эксперта, если они остались в хранилище, видны институции, потратившей
  квоту, а не только текущее CV: политика опознаёт CV по виду файла и владельцу.
  Это те же персональные данные того же человека, полученные по тому же праву.
